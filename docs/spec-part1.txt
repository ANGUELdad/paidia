Πλήρης Λειτουργική και Τεχνική Προδιαγραφή
Συστήματος
Διαχείριση Προσωπικού, Παιδιών, Βαρδιών, Ημερήσιου
Προγράμματος, Αποθήκης και Τροφίμων
**Έκδοση:** 1.0
**Σκοπός εγγράφου:** Να δοθεί σε software engineer και σε LLM coding assistant,
ώστε να υλοποιηθεί ενιαία web εφαρμογή για τη λειτουργία δύο κατοικιών/μονάδων
φιλοξενίας και του προσωπικού τους.
---
1. Σύνοψη του συστήματος
Η εφαρμογή θα αποτελεί ένα ενιαίο πληροφοριακό σύστημα για:
1. Διαχείριση προσωπικού.
2. Διαχείριση παιδιών/νέων.
3. Διαχείριση δύο χώρων:
- **Καλύβια / Villa**
- **Λιμενάρια**
4. Εβδομαδιαίο πρόγραμμα.
5. Ημερήσια κατανομή παιδιών και προσωπικού.
6. Βάρδιες, συμπεριλαμβανομένων 24ωρων βαρδιών.
7. Καταγραφή δραστηριοτήτων.
8. Έλεγχο παρουσιών και αλλαγών βάρδιας.
9. Διαχείριση ψυγείου, αποθήκης και τροφίμων.
10. Λίστα εβδομαδιαίων αγορών.
11. Παραλαβή ειδών από supermarket.
12. Ιστορικό κινήσεων και πλήρες audit trail.
13. Προφίλ χρηστών με γρήγορο PIN.
14. Διαφορετικά δικαιώματα πρόσβασης.
15. Εβδομαδιαίες υπενθυμίσεις μέσω email.
16. Αποθήκευση φωτογραφιών σε ιδιόκτητο server.
17. Φιλοξενία του frontend και των βασικών serverless λειτουργιών στο Vercel.
18. Αυτόματη βοήθεια με AI για την εισαγωγή λιστών αγορών και την οργάνωση
δεδομένων.

----- page 2 -----
Το σύστημα **δεν πρέπει να βασίζεται στη λογική “ένας φροντιστής = ένα παιδί”**.
Ένας φροντιστής μπορεί να έχει:
- ένα παιδί,
- δύο παιδιά,
- μικρή ομάδα,
- μεγαλύτερη ομάδα,
- παιδιά από διαφορετικές κατοικίες,
- ευέλικτο υποστηρικτικό ρόλο,
- δικό του πρόγραμμα με ομάδα,
- ή εφεδρικό ρόλο ανάλογα με τις ανάγκες.

2. Βασική φιλοσοφία λειτουργίας
2.1 Δύο επίπεδα προγραμματισμού
Το σύστημα πρέπει να υποστηρίζει δύο διαφορετικά επίπεδα:
Α. Εβδομαδιαίος προγραμματισμός
Συμπληρώνεται μία φορά την εβδομάδα και περιλαμβάνει:
- ποιος εργάζεται,
- σε ποιο χώρο,
- με ποια παιδιά,
- ποιες ώρες,
- ποια δραστηριότητα,
- πρωινό πρόγραμμα,
- απογευματινή φροντίδα,
- βραδινό πρόγραμμα,
- ειδικές σημειώσεις,
- εβδομαδιαίες δραστηριότητες,
- απαιτούμενα υλικά,
- αλλαγές ή εξαιρέσεις.

----- page 3 -----
Β. Ημερήσιος προγραμματισμός
Οριστικοποιείται καθημερινά, κατά την απογευματινή/μεσημεριανή ομαδική
τηλεδιάσκεψη.
Η βασική αρχή είναι:
- Το εβδομαδιαίο πρόγραμμα αποτελεί **προσχέδιο / Grundplanung**.
- Η τελική κατανομή γίνεται καθημερινά.
- Οι ομάδες μπορούν να αλλάζουν.
- Ένα παιδί μπορεί να μετακινηθεί από μία ομάδα σε άλλη.
- Ένας φροντιστής μπορεί να αναλάβει διαφορετική ομάδα από αυτή του αρχικού
σχεδίου.
- Ορισμένοι εργαζόμενοι μπορούν να έχουν “flexible support” ρόλο.

- να κλειδώνει προσωρινά μετά από πολλές αποτυχημένες προσπάθειες,
- να έχει optional δεύτερο επίπεδο ασφάλειας για admins.

9. Business rules και αποφυγή λογικών λαθών
Το σύστημα πρέπει να εντοπίζει και να αποτρέπει παράλογες καταστάσεις.
9.1 Παραδείγματα validation
Προσωπικό

----- page 16 -----
- Ένας φροντιστής δεν μπορεί να βρίσκεται ταυτόχρονα σε δύο διαφορετικά σπίτια.
- Δεν μπορεί να έχει επικαλυπτόμενες βάρδιες χωρίς override.
- Δεν μπορεί να είναι σε ρεπό και ταυτόχρονα σε ενεργή βάρδια.
- Δεν μπορεί να λήγει μία βάρδια μετά την έναρξη της επόμενης χωρίς warning.
- Μία 24ωρη βάρδια πρέπει να έχει σαφή έναρξη και λήξη.
- Δεν επιτρέπεται αλλαγή locked εβδομάδας χωρίς admin override.
Παιδιά
- Ένα παιδί δεν μπορεί να βρίσκεται σε δύο ομάδες την ίδια ώρα.
- Δεν μπορεί να είναι ταυτόχρονα σε Villa και Λιμενάρια.
- Δεν μπορεί να είναι σε δραστηριότητα αν έχει καταγραφεί ως absent.
- Αν ένα παιδί αποχωρήσει από το project, δεν πρέπει να εμφανίζεται ενεργό σε νέα
προγράμματα.
Ομάδες
- Μία ομάδα μπορεί να έχει πολλά παιδιά.
- Ένας φροντιστής μπορεί να έχει πολλά παιδιά.
- Μία δραστηριότητα μπορεί να έχει πολλούς φροντιστές.
- Flexible support δεν σημαίνει αποκλειστική ομάδα.
Κάλυψη
παιδιά.
- Πρέπει να υπάρχει τουλάχιστον ένας ενεργός υπεύθυνος ανά σπίτι όταν διαμένουν
- Να υπάρχει warning αν μία κατοικία εμφανίζεται χωρίς προσωπικό.
- Να υπάρχει warning αν υπάρχει νυχτερινή διαμονή χωρίς δηλωμένη 24ωρη ή βραδινή
κάλυψη.
- Να υπάρχει warning για υπερβολικά μεγάλη ομάδα με έναν μόνο φροντιστή, με
configurable threshold.
- Το warning δεν πρέπει να απαγορεύει αυτόματα τη λειτουργία, επειδή οι πραγματικές
ανάγκες διαφέρουν. Θα επιτρέπεται override με αιτιολογία.

11. Λίστα αγορών supermarket
11.1 Ροή Παρασκευής
Κάθε Παρασκευή:
1. Οι φροντιστές ετοιμάζουν λίστες.
2. Οι λίστες εισάγονται στην εφαρμογή.
3. Το AI αναλύει το κείμενο.
4. Δημιουργεί δομημένα προϊόντα.
5. Ο φροντιστής ελέγχει και διορθώνει.
6. Ο υπεύθυνος εγκρίνει.
7. Η λίστα αλλάζει σε “To Buy”.
8. Μετά την επίσκεψη στο supermarket γίνεται παραλαβή.
9. Κάθε item σημειώνεται:
- αγορασμένο,
- μη διαθέσιμο,
- μερικώς αγορασμένο,
- αντικαταστάθηκε,

----- page 21 -----
- ακυρώθηκε.
10. Τα αγορασμένα είδη περνούν αυτόματα στο inventory.
11.2 Status προϊόντος στη λίστα
- Suggested
- Draft
- Approved
- To Buy
- In Store
- Purchased
- Partially Purchased
- Not Available
- Replaced
- Cancelled
- Received
- Stored
11.3 “Expected incoming stock”
Μόλις εγκριθεί η λίστα, τα προϊόντα μπορούν να εμφανίζονται στο inventory ως:
- expected,
- not yet received.
Δεν πρέπει να υπολογίζονται ως πραγματικό διαθέσιμο απόθεμα.
Με την παραλαβή:
- μετατρέπονται σε actual stock,
- επιλέγεται χώρος αποθήκευσης,
- καταγράφεται ποσότητα,
- καταγράφεται ποιος τα παρέλαβε.
11.4 Μη διαθέσιμο προϊόν

----- page 22 -----
Αν ένα προϊόν δεν βρεθεί:
- μένει ανοιχτό,
- σημειώνεται “Not Available”,
- δεν προστίθεται στο inventory,
- εμφανίζεται ως έλλειψη,
- μπορεί να μεταφερθεί στην επόμενη λίστα,
- μπορεί να προταθεί substitute.
11.5 AI parsing
Το AI θα πρέπει να μετατρέπει κείμενα όπως:
> “Nutella 2, Milch light 2, Wasser groß 4, kleine Wasser 3, Nektarinen 10–12”
σε structured rows:
| Product | Quantity | Unit | Category | Notes |
|---|---:|---|---|---|
| Nutella | 2 | τεμάχια | Pantry | |
| Milch light | 2 | τεμάχια | Refrigerator | |
| Wasser groß | 4 | packs/bottles | Drinks | confirmation needed |
| Nektarinen | 10–12 | τεμάχια | Fruit | |
Το AI δεν πρέπει να αποθηκεύει αυτόματα χωρίς επιβεβαίωση.

14.1 Storage strategy

----- page 26 -----

- file id,
- storage path,
- thumbnail,
- uploader,
- timestamp,

----- page 27 -----
- linked entity.
5. Το Vercel δεν κρατά το binary αρχείο.
14.4 Πρόσβαση

- να μην είναι public,
- να χρησιμοποιούν signed URLs,
- να λήγουν,
- να έχουν role-based access,

32. Drag-and-Drop λειτουργία και φίλτρα
προβολής
32.1 Γενική απαίτηση ευχρηστίας
Η εφαρμογή πρέπει να είναι όσο το δυνατόν πιο εύκολη στη χρήση και να βασίζεται
κυρίως σε:
- drag-and-drop,
- μεγάλα καθαρά κουμπιά,
- κάρτες χρηστών και παιδιών,
- χρωματική διάκριση καταστάσεων,
- ελάχιστη πληκτρολόγηση,
- γρήγορες επιλογές,
- άμεση αποθήκευση,
- undo/redo,
- σαφή προειδοποίηση πριν από κρίσιμη αλλαγή.
Η βασική λογική είναι ότι ο χρήστης θα πρέπει να μπορεί να οργανώνει το πρόγραμμα
κυρίως μετακινώντας κάρτες στην οθόνη.
