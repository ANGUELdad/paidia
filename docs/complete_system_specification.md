# Πλήρης Λειτουργική και Τεχνική Προδιαγραφή Συστήματος  
## Διαχείριση Προσωπικού, Παιδιών, Βαρδιών, Ημερήσιου Προγράμματος, Αποθήκης και Τροφίμων

**Έκδοση:** 1.0  
**Σκοπός εγγράφου:** Να δοθεί σε software engineer και σε LLM coding assistant, ώστε να υλοποιηθεί ενιαία web εφαρμογή για τη λειτουργία δύο κατοικιών/μονάδων φιλοξενίας και του προσωπικού τους.

---

# 1. Σύνοψη του συστήματος

Η εφαρμογή θα αποτελεί ένα ενιαίο πληροφοριακό σύστημα για:

1. Διαχείριση προσωπικού.
2. Διαχείριση παιδιών/νέων.
3. Διαχείριση δύο χώρων:
   - **Καλύβια / Villa**
   - **Λιμενάρια**
4. Εβδομαδιαίο πρόγραμμα.
5. Ημερήσια κατανομή παιδιών και προσωπικού.
6. Βάρδιες, συμπεριλαμβανομένων 24ωρων βαρδιών.
7. Καταγραφή δραστηριοτήτων.
8. Έλεγχο παρουσιών και αλλαγών βάρδιας.
9. Διαχείριση ψυγείου, αποθήκης και τροφίμων.
10. Λίστα εβδομαδιαίων αγορών.
11. Παραλαβή ειδών από supermarket.
12. Ιστορικό κινήσεων και πλήρες audit trail.
13. Προφίλ χρηστών με γρήγορο PIN.
14. Διαφορετικά δικαιώματα πρόσβασης.
15. Εβδομαδιαίες υπενθυμίσεις μέσω email.
16. Αποθήκευση φωτογραφιών σε ιδιόκτητο server.
17. Φιλοξενία του frontend και των βασικών serverless λειτουργιών στο Vercel.
18. Αυτόματη βοήθεια με AI για την εισαγωγή λιστών αγορών και την οργάνωση δεδομένων.

Το σύστημα **δεν πρέπει να βασίζεται στη λογική “ένας φροντιστής = ένα παιδί”**. Ένας φροντιστής μπορεί να έχει:

- ένα παιδί,
- δύο παιδιά,
- μικρή ομάδα,
- μεγαλύτερη ομάδα,
- παιδιά από διαφορετικές κατοικίες,
- ευέλικτο υποστηρικτικό ρόλο,
- δικό του πρόγραμμα με ομάδα,
- ή εφεδρικό ρόλο ανάλογα με τις ανάγκες.

# 2. Βασική φιλοσοφία λειτουργίας

## 2.1 Δύο επίπεδα προγραμματισμού

Το σύστημα πρέπει να υποστηρίζει δύο διαφορετικά επίπεδα:

### Α. Εβδομαδιαίος προγραμματισμός
Συμπληρώνεται μία φορά την εβδομάδα και περιλαμβάνει:

- ποιος εργάζεται,
- σε ποιο χώρο,
- με ποια παιδιά,
- ποιες ώρες,
- ποια δραστηριότητα,
- πρωινό πρόγραμμα,
- απογευματινή φροντίδα,
- βραδινό πρόγραμμα,
- ειδικές σημειώσεις,
- εβδομαδιαίες δραστηριότητες,
- απαιτούμενα υλικά,
- αλλαγές ή εξαιρέσεις.

### Β. Ημερήσιος προγραμματισμός
Οριστικοποιείται καθημερινά, κατά την απογευματινή/μεσημεριανή ομαδική τηλεδιάσκεψη.

Η βασική αρχή είναι:

- Το εβδομαδιαίο πρόγραμμα αποτελεί **προσχέδιο / Grundplanung**.
- Η τελική κατανομή γίνεται καθημερινά.
- Οι ομάδες μπορούν να αλλάζουν.
- Ένα παιδί μπορεί να μετακινηθεί από μία ομάδα σε άλλη.
- Ένας φροντιστής μπορεί να αναλάβει διαφορετική ομάδα από αυτή του αρχικού σχεδίου.
- Ορισμένοι εργαζόμενοι μπορούν να έχουν “flexible support” ρόλο.

# 4. Χρήστες και προφίλ

## 4.1 Κεντρική οθόνη επιλογής προφίλ

Με την είσοδο στην εφαρμογή, δεν πρέπει να εμφανίζεται απλή φόρμα email/password.

Η πρώτη οθόνη πρέπει να είναι ένα όμορφο **profile selection panel**, αντίστοιχο με profile picker εφαρμογών streaming.

Κάθε προφίλ να εμφανίζει:

- φωτογραφία ή avatar,
- όνομα,
- ρόλο,
- προαιρετικά χώρο εργασίας,
- κατάσταση online/offline,
- προαιρετικά ένδειξη “σε βάρδια”.

Παράδειγμα:

- Zoi
- Angelos
- Dimi
- Dora
- Karin
- Claudio
- Löhri
- Amalia
- άλλοι μελλοντικοί εργαζόμενοι

Μετά την επιλογή προφίλ:

1. Ο χρήστης πληκτρολογεί σύντομο PIN.
2. Το σύστημα ελέγχει το PIN.
3. Δημιουργείται authenticated session.
4. Καταγράφεται:
   - user ID,
   - ημερομηνία,
   - ώρα,
   - IP,
   - user agent,
   - device fingerprint όπου επιτρέπεται,
   - session ID.

## 4.2 PIN

Το PIN πρέπει:

- να είναι τουλάχιστον 4–6 ψηφία,
- να αποθηκεύεται hashed,
- να μην αποθηκεύεται ποτέ ως plain text,
- να μπορεί να αλλάζει από τον χρήστη ή από admin,
- να κλειδώνει προσωρινά μετά από πολλές αποτυχημένες προσπάθειες,
- να έχει optional δεύτερο επίπεδο ασφάλειας για admins.

# 9. Business rules και αποφυγή λογικών λαθών

Το σύστημα πρέπει να εντοπίζει και να αποτρέπει παράλογες καταστάσεις.

## 9.1 Παραδείγματα validation

### Προσωπικό
- Ένας φροντιστής δεν μπορεί να βρίσκεται ταυτόχρονα σε δύο διαφορετικά σπίτια.
- Δεν μπορεί να έχει επικαλυπτόμενες βάρδιες χωρίς override.
- Δεν μπορεί να είναι σε ρεπό και ταυτόχρονα σε ενεργή βάρδια.
- Δεν μπορεί να λήγει μία βάρδια μετά την έναρξη της επόμενης χωρίς warning.
- Μία 24ωρη βάρδια πρέπει να έχει σαφή έναρξη και λήξη.
- Δεν επιτρέπεται αλλαγή locked εβδομάδας χωρίς admin override.

### Παιδιά
- Ένα παιδί δεν μπορεί να βρίσκεται σε δύο ομάδες την ίδια ώρα.
- Δεν μπορεί να είναι ταυτόχρονα σε Villa και Λιμενάρια.
- Δεν μπορεί να είναι σε δραστηριότητα αν έχει καταγραφεί ως absent.
- Αν ένα παιδί αποχωρήσει από το project, δεν πρέπει να εμφανίζεται ενεργό σε νέα προγράμματα.

### Ομάδες
- Μία ομάδα μπορεί να έχει πολλά παιδιά.
- Ένας φροντιστής μπορεί να έχει πολλά παιδιά.
- Μία δραστηριότητα μπορεί να έχει πολλούς φροντιστές.
- Flexible support δεν σημαίνει αποκλειστική ομάδα.

### Κάλυψη
- Πρέπει να υπάρχει τουλάχιστον ένας ενεργός υπεύθυνος ανά σπίτι όταν διαμένουν παιδιά.
- Να υπάρχει warning αν μία κατοικία εμφανίζεται χωρίς προσωπικό.
- Να υπάρχει warning αν υπάρχει νυχτερινή διαμονή χωρίς δηλωμένη 24ωρη ή βραδινή κάλυψη.
- Να υπάρχει warning για υπερβολικά μεγάλη ομάδα με έναν μόνο φροντιστή, με configurable threshold.
- Το warning δεν πρέπει να απαγορεύει αυτόματα τη λειτουργία, επειδή οι πραγματικές ανάγκες διαφέρουν. Θα επιτρέπεται override με αιτιολογία.

# 10. Διαχείριση ψυγείου, αποθήκης και τροφίμων

## 10.1 Ενιαία βάση αποθεμάτων

Κάθε item θα έχει:

- id,
- όνομα,
- κατηγορία,
- brand,
- μονάδα μέτρησης,
- ποσότητα,
- location,
- storage zone,
- ημερομηνία αγοράς,
- ημερομηνία παραλαβής,
- ημερομηνία λήξης,
- batch,
- κόστος,
- supplier,
- status,
- created by,
- last updated by.

## 10.2 Τοποθεσίες αποθήκευσης

Παραδείγματα:

- Villa Storage Room

- Limenaria Storage Room

Το σύστημα πρέπει να γνωρίζει **τι υπάρχει, πόσο υπάρχει και πού βρίσκεται**.

## 10.3 Κίνηση προϊόντος

Κάθε φορά που ένα προϊόν:

- εισέρχεται,
- αφαιρείται,
- καταναλώνεται,
- μεταφέρεται,
- απορρίπτεται,
- λήγει,
- χαλάει,
- χρησιμοποιείται σε δραστηριότητα,
- δίνεται σε παιδί,
- μεταφέρεται σε άλλο σπίτι,

πρέπει να δημιουργείται immutable inventory transaction.

Πεδία transaction:

# 11. Λίστα αγορών supermarket

## 11.1 Ροή Παρασκευής

Κάθε Παρασκευή:

1. Οι φροντιστές ετοιμάζουν λίστες.
2. Οι λίστες εισάγονται στην εφαρμογή.
3. Το AI αναλύει το κείμενο.
4. Δημιουργεί δομημένα προϊόντα.
5. Ο φροντιστής ελέγχει και διορθώνει.
6. Ο υπεύθυνος εγκρίνει.
7. Η λίστα αλλάζει σε “To Buy”.
8. Μετά την επίσκεψη στο supermarket γίνεται παραλαβή.
9. Κάθε item σημειώνεται:
   - αγορασμένο,
   - μη διαθέσιμο,
   - μερικώς αγορασμένο,
   - αντικαταστάθηκε,
   - ακυρώθηκε.
10. Τα αγορασμένα είδη περνούν αυτόματα στο inventory.

## 11.2 Status προϊόντος στη λίστα

- Suggested
- Draft
- Approved
- To Buy
- In Store
- Purchased
- Partially Purchased
- Not Available
- Replaced
- Cancelled
- Received
- Stored

## 11.3 “Expected incoming stock”

Μόλις εγκριθεί η λίστα, τα προϊόντα μπορούν να εμφανίζονται στο inventory ως:

- expected,
- not yet received.

Δεν πρέπει να υπολογίζονται ως πραγματικό διαθέσιμο απόθεμα.

Με την παραλαβή:

- μετατρέπονται σε actual stock,
- επιλέγεται χώρος αποθήκευσης,
- καταγράφεται ποσότητα,
- καταγράφεται ποιος τα παρέλαβε.

## 11.4 Μη διαθέσιμο προϊόν

Αν ένα προϊόν δεν βρεθεί:

- μένει ανοιχτό,
- σημειώνεται “Not Available”,
- δεν προστίθεται στο inventory,
- εμφανίζεται ως έλλειψη,
- μπορεί να μεταφερθεί στην επόμενη λίστα,
- μπορεί να προταθεί substitute.

## 11.5 AI parsing

Το AI θα πρέπει να μετατρέπει κείμενα όπως:

> “Nutella 2, Milch light 2, Wasser groß 4, kleine Wasser 3, Nektarinen 10–12”

σε structured rows:

| Product | Quantity | Unit | Category | Notes |
|---|---:|---|---|---|
| Nutella | 2 | τεμάχια | Pantry | |
| Milch light | 2 | τεμάχια | Refrigerator | |
| Wasser groß | 4 | packs/bottles | Drinks | confirmation needed |
| Nektarinen | 10–12 | τεμάχια | Fruit | |

Το AI δεν πρέπει να αποθηκεύει αυτόματα χωρίς επιβεβαίωση.

# 14. Φωτογραφίες και αρχεία

## 14.1 Storage strategy

Οι φωτογραφίες δεν πρέπει να αποθηκεύονται στο Vercel filesystem.

Προτεινόμενη αρχιτεκτονική:

- Vercel:
  - frontend,
  - Next.js app,
  - API routes όπου απαιτείται,
  - authentication callbacks,
  - βασικά static assets.

- Ιδιόκτητος server:
  - φωτογραφίες,
  - μεγάλα αρχεία,
  - media,
  - backups,
  - πιθανώς object storage-compatible service.

## 14.2 Προτεινόμενες λύσεις

Ο server μπορεί να τρέχει:

- MinIO,
- S3-compatible storage,
- secure file API,
- signed URL service,
- thumbnail generator.

## 14.3 Upload flow

1. Ο χρήστης επιλέγει φωτογραφία.
2. Το frontend ζητά signed upload URL.
3. Η φωτογραφία ανεβαίνει απευθείας στον server.
4. Η βάση κρατά:
   - file id,
   - storage path,
   - thumbnail,
   - uploader,
   - timestamp,
   - linked entity.
5. Το Vercel δεν κρατά το binary αρχείο.

## 14.4 Πρόσβαση

Οι φωτογραφίες πρέπει:

- να μην είναι public,
- να χρησιμοποιούν signed URLs,
- να λήγουν,
- να έχουν role-based access,
- να μην εμφανίζονται χωρίς authentication.

# 37. Γρήγορη και εύκολη διαχείριση αγορών

## 37.1 Quick Shopping Mode

- Μερικώς
- Αντικαταστάθηκε
- Ακύρωση

## 37.2 Swipe actions

Σε κινητό:

- swipe δεξιά = αγοράστηκε,
- swipe αριστερά = δεν υπήρχε,

## 37.3 Bulk completion

Να μπορεί ο χρήστης:

- να επιλέξει πολλά items,
- να τα σημειώσει όλα “Αγοράστηκε”,
- να τα μεταφέρει όλα στο inventory,
- να τα αφαιρέσει από τη λίστα,
- να μεταφέρει τα μη διαθέσιμα στην επόμενη εβδομάδα.

## 37.4 Αφαίρεση από τη λίστα

Όταν ένα προϊόν ολοκληρωθεί:

- παραμένει στο ιστορικό,
- φεύγει από την ενεργή λίστα,
- μετακινείται στην ενότητα “Ολοκληρωμένα”,
- δεν διαγράφεται πραγματικά.

## 37.5 Λίστες βάσει προτύπων

Να υπάρχουν templates:

- εβδομαδιαία βασικά,
- καθαριστικά,
- πρωινό,
- φρούτα/λαχανικά,
- κρέατα,
- παιδικά είδη,
- προσωπική υγιεινή,
- Villa,
- Limenaria.

## 37.6 Δημιουργία από προηγούμενες λίστες

Να μπορεί να δημιουργηθεί νέα λίστα από:

- προηγούμενη εβδομάδα,
- μέσο όρο τελευταίων 4 εβδομάδων,
- χαμηλά αποθέματα,
- συχνά αγοραζόμενα,
- items που δεν υπήρχαν,
- AI suggestion.

## 37.7 Αυτόματη αφαίρεση βάσει stock

Πριν προστεθεί item στη λίστα, το σύστημα πρέπει να ελέγχει:

- υπάρχει ήδη αρκετή ποσότητα;
- υπάρχει αναμενόμενη παραλαβή;
- υπάρχει duplicate στην ίδια λίστα;
- υπάρχει το ίδιο item σε άλλη λίστα;
- υπάρχει substitute διαθέσιμο;

Ο χρήστης πρέπει να μπορεί να κάνει override.

# 40. Νέα acceptance criteria

1. Δεν μπορεί να δημιουργηθεί ίδια ανάθεση δύο φορές χωρίς warning.
2. Δεν μπορεί να προστεθεί το ίδιο παιδί δύο φορές στην ίδια ομάδα.
3. Δεν μπορεί να δημιουργηθεί ίδιο inventory transaction από διπλό click.
4. Υπάρχει πλήρες Activity Tab.
5. Όλες οι αλλαγές δείχνουν before/after.
6. Οι αγορές ολοκληρώνονται με ένα tap.
7. Υπάρχει bulk completion.
8. Τα ολοκληρωμένα items δεν διαγράφονται αλλά αρχειοθετούνται.
9. Οι λίστες δημιουργούνται από templates και stock.
10. Τα conflicts μεταξύ δύο χρηστών εμφανίζονται καθαρά.
11. Το σύστημα διαχειρίζεται offline και retry χωρίς duplicates.
12. Όλα τα critical operations είναι idempotent.
13. Τα filters δεν αποκρύπτουν ενεργό error χωρίς ένδειξη.
14. Υπάρχει override μόνο με αιτιολογία.
15. Κάθε override εμφανίζεται στο Activity Tab.

# 55. Συνολικός μηχανισμός πρόληψης σφαλμάτων, bugs και ασυνεπειών

## 55.1 Κεντρική αρχή αξιοπιστίας

Το σύστημα πρέπει να θεωρεί ότι ο χρήστης μπορεί να πατήσει δύο φορές το ίδιο κουμπί, δύο χρήστες μπορεί να αλλάξουν τα ίδια δεδομένα ταυτόχρονα, η σύνδεση μπορεί να κοπεί οποιαδήποτε στιγμή, ένα AI αποτέλεσμα μπορεί να είναι λάθος, μία λίστα μπορεί να διαβαστεί λανθασμένα και ένα record μπορεί να είναι τεχνικά έγκυρο αλλά επιχειρησιακά παράλογο.

Απαιτούνται ταυτόχρονα:

- client-side και server-side validation,
- database constraints,
- idempotency keys,
- audit trail,
- duplicate prevention,
- confirmation για κρίσιμες αλλαγές,
- undo όπου είναι ασφαλές,
- reconciliation jobs,
- admin review queues.

## 55.2 Κατηγορίες σφαλμάτων

### Hard error
Η αποθήκευση απαγορεύεται, π.χ. λήξη βάρδιας πριν από την έναρξη, ίδιο παιδί δύο φορές στην ίδια ομάδα, αρνητικό stock χωρίς correction, μη εξουσιοδοτημένη πρόσβαση ή inventory transaction χωρίς προϊόν.

### Warning
Η ενέργεια επιτρέπεται μόνο μετά από επιβεβαίωση, π.χ. πολύ μεγάλη ομάδα για έναν φροντιστή, αλλαγή τελευταίας στιγμής, προϊόν που υπάρχει ήδη σε επαρκές stock ή event χωρίς υλικά.

### Informational notice
Η ενέργεια επιτρέπεται, αλλά εμφανίζεται χρήσιμη πληροφορία, π.χ. το ίδιο προϊόν αγοράστηκε την προηγούμενη εβδομάδα ή υπάρχει event που πιθανόν το χρειάζεται.

# 57. Επιπλέον edge cases ψυγείων, αποθήκης και προμηθειών

## 57.1 Canonical προϊόντα και aliases

Το ίδιο προϊόν μπορεί να εμφανίζεται ως «Γάλα», «Γάλα light», «Milch light», «Light milk» ή «γάλα 1,5%».

Κάθε προϊόν πρέπει να έχει:

- canonical product,
- aliases,
- normalized name,
- category,
- brand,
- package size,
- unit,
- barcode όπου υπάρχει.

Δεν επιτρέπεται αυτόματη συγχώνευση όταν δεν υπάρχει αρκετή βεβαιότητα.

## 57.2 Μονάδες μέτρησης

Υποστηρίζονται τεμάχια, πακέτα, κιλά, γραμμάρια, λίτρα, ml, κουτιά, μπουκάλια, σακούλες και ρολά.

Edge cases:

- 2 πακέτα x 6 τεμάχια,
- 1,5 kg,
- 500 g και 0,5 kg,
- ανοιγμένο ή μισό πακέτο,
- διαφορετικά μεγέθη συσκευασίας,
- μη ασφαλής μετατροπή χωρίς package metadata.

## 57.3 Ακεραιότητα stock

Πρέπει να αποτρέπονται:

- αρνητικό stock,
- διπλή παραλαβή ή αφαίρεση,
- transfer χωρίς αντίστοιχη αφαίρεση από source,
- item σε λάθος storage zone,
- expired προϊόν ως διαθέσιμο,
- προϊόν που χρησιμοποιήθηκε ενώ ήταν reserved,
- αλλαγή ποσότητας χωρίς transaction.

Οι μεταφορές γίνονται ως μία atomic database transaction.

## 57.4 Shared house inventory

Για το Ψυγείο Κοριτσιών, το Ψυγείο Φροντιστών και την Κοινή Αποθήκη απαιτούνται:

- κοινή συνολική εικόνα,
- ξεχωριστή φυσική θέση,
- ξεχωριστό ιστορικό κατανάλωσης,
- εσωτερικές μεταφορές,
- αποφυγή διπλού υπολογισμού,
- διάκριση ownership/use category από physical location.

## 57.5 Φωτογραφίες inventory

Η φωτογραφία αποτελεί τεκμηρίωση, όχι μοναδική πηγή αλήθειας. Πρέπει να χειρίζεται φωτογραφία λάθος ψυγείου, παλιού stock, duplicate upload, αποτυχημένο upload, media server offline και φωτογραφία χωρίς σύνδεση με απογραφή.

# 58. AI για ανάγνωση λιστών αγορών

## 58.1 Υποστηριζόμενες πηγές

Το AI πρέπει να διαβάζει:

- απλό κείμενο,
- επικολλημένο μήνυμα,
- φωτογραφία χειρόγραφης ή τυπωμένης λίστας,
- PDF,
- screenshot,
- TXT,
- CSV,
- Excel,
- email content,
- προηγούμενη λίστα της εφαρμογής.

## 58.2 AI extraction pipeline

1. Upload ή επικόλληση.
2. Ανίχνευση τύπου αρχείου.
3. Εξαγωγή κειμένου.
4. Ανίχνευση γλώσσας.
5. Διάσπαση σε προϊόντα.
6. Αναγνώριση ποσότητας και μονάδας.
7. Αναγνώριση brand και package size.
8. Κατηγοριοποίηση.
9. Αντιστοίχιση με canonical product.
10. Έλεγχος duplicates.
11. Έλεγχος υπάρχοντος και αναμενόμενου stock.
12. Προβολή draft.
13. Ανθρώπινη επιβεβαίωση.
14. Αποθήκευση στην ενεργή λίστα.
15. Αρχειοθέτηση του αρχικού αρχείου και του extracted text.

## 58.3 Confidence score

Κάθε extracted item έχει:

- υψηλή,
- μέτρια,
- χαμηλή βεβαιότητα.

Σε χαμηλή βεβαιότητα ζητείται επιβεβαίωση. Παράδειγμα: «Νερά μεγάλα 4» σημαίνει 4 μπουκάλια ή 4 εξάδες;

## 58.4 Duplicate detection από AI

Το AI πρέπει να αναγνωρίζει ότι:

- Nutella x2,
- 2 Nutella,
- Nutella δύο φορές

πιθανόν είναι μία εγγραφή ποσότητας 2.

Δεν συγχωνεύει αυτόματα προϊόντα διαφορετικού brand, μεγέθους ή τύπου.

## 58.5 Έλεγχος stock πριν από την αγορά

Για κάθε πρόταση εμφανίζονται:

- τρέχον stock,
- αναμενόμενο stock,
- μέση εβδομαδιαία κατανάλωση,
- εκτιμώμενες ημέρες επάρκειας,
- προτεινόμενη ποσότητα αγοράς.

Το AI δεν αφαιρεί αυτόματα προϊόν από τη λίστα μόνο επειδή υπάρχει stock.

## 58.6 Αρχειοθέτηση και versioning

Για κάθε εισαγόμενη λίστα αποθηκεύονται:

- αρχικό αρχείο,
- uploader,
- ημερομηνία/ώρα,
- extracted text,
- AI αποτέλεσμα,
- confidence ανά item,
- διορθώσεις χρήστη,
- τελική approved list,
- version history.

## 58.7 AI learning από διορθώσεις

Το AI μπορεί να μαθαίνει οργανωτικά:

- aliases,
- συνηθισμένες μονάδες,
- brands,
- ποσότητες,
- συχνά OCR λάθη.

Δεν αλλάζει ιστορικά records και δεν εκτελεί αλλαγές χωρίς επιβεβαίωση.

# 59. Shopping AI edge cases

Το AI πρέπει να χειρίζεται:

- δυσανάγνωστο χειρόγραφο,
- ελληνικά και γερμανικά στην ίδια λίστα,
- ορθογραφικά λάθη και συντομογραφίες,
- ασαφή ποσότητα,
- εύρος όπως 10–12,
- δύο προϊόντα στην ίδια γραμμή,
- διαγραμμένο προϊόν,
- φωτογραφία με σκιά ή περιστροφή,
- duplicate pages,
- ίδιο αρχείο δύο φορές,
- προϊόν χωρίς ποσότητα,
- ποσότητα χωρίς προϊόν,
- προϊόν για συγκεκριμένο σπίτι ή event,
- προϊόν ήδη σε άλλη λίστα,
- μη τρόφιμο μέσα σε λίστα τροφίμων,
- OCR σφάλματα 1/7, 0/6, kg/g,
- αγορά χωρίς να υπάρχει στη λίστα,
- αντικατάσταση προϊόντος,
- μερική αγορά.

# 60. Bugs που πρέπει να προληφθούν

## 60.1 Frontend

- διπλό click,
- stale UI,
- accidental drag,
- χαμένη αλλαγή λόγω refresh,
- φίλτρο που κρύβει ενεργό error,
- λάθος sorting ημερών,
- mobile keyboard που καλύπτει κουμπιά,
- μη ορατό confirmation,
- accidental destructive action.

## 60.2 API

- retry που δημιουργεί duplicate,
- timeout ενώ η ενέργεια ολοκληρώθηκε,
- race condition,
- missing idempotency key,
- malformed date,
- oversized upload,
- API version mismatch.

## 60.3 Database

- orphan records,
- deadlocks,
- duplicate rows,
- missing foreign keys,
- inconsistent counters,
- failed migration,
- wrong timezone,
- soft-deleted record που επανεμφανίζεται,
- partial transaction.

## 60.4 Background jobs

- duplicate email,
- reminder μετά την ολοκλήρωση,
- AI job δύο φορές,
- endless retry loop,
- job σε λάθος timezone,
- notification σε ανενεργό χρήστη.

## 60.5 File storage

- broken ή expired signed URL,
- orphan file,
- database record χωρίς αρχείο,
- αρχείο χωρίς database record,
- checksum mismatch,
- storage full,
- backup χωρίς media,
- thumbnail failure.

# 61. Αυτόματοι έλεγχοι συμφωνίας

## Καθημερινά

- stock όχι αρνητικό,
- ενεργές βάρδιες με προσωπικό,
- παιδιά όχι διπλοανατεθειμένα,
- daily plan οριστικοποιημένο,
- pending daily call items,
- μη ολοκληρωμένα handovers.

## Κάθε Παρασκευή

- shopping list vs purchased,
- purchased vs received,
- received vs stored,
- missing items,
- duplicated products,
- unresolved low-confidence AI items.

## Κάθε Κυριακή

- κάλυψη επόμενης εβδομάδας,
- επιβεβαιώσεις προσωπικού,
- approvals events,
- πρόσφατη απογραφή ψυγείων,
- low stock report.

## Μηνιαίως

- inventory reconciliation,
- inactive users,
- stale AI memory,
- orphan files,
- duplicate products,
- audit integrity check.

# 62. Νέα acceptance criteria αξιοπιστίας

1. Το ίδιο API request δεν δημιουργεί δεύτερη εγγραφή.
2. Δύο ταυτόχρονες αλλαγές παράγουν conflict dialog.
3. Η μεταφορά stock είναι atomic.
4. Το AI δεν αποθηκεύει λίστα χωρίς ανθρώπινη επιβεβαίωση.
5. Κάθε AI item έχει confidence score.
6. Η αρχική λίστα και οι διορθώσεις αρχειοθετούνται.
7. Υποστηρίζονται aliases προϊόντων.
8. Υποστηρίζονται ελληνικά και γερμανικά στην ίδια λίστα.
9. Εντοπίζονται fuzzy duplicates.
10. Δεν επιτρέπεται αρνητικό stock χωρίς admin correction.
11. Κάθε κρίσιμη ενέργεια έχει idempotency key.
12. Υπάρχει καθημερινό και εβδομαδιαίο reconciliation.
13. Low-confidence AI εγγραφές δεν περνούν αυτόματα.
14. Failed uploads δεν αφήνουν ψεύτικα ολοκληρωμένα records.
15. Το Activity Tab καταγράφει AI extraction, ανθρώπινη διόρθωση και τελική έγκριση.
