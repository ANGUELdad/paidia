34. Νέα acceptance criteria για drag-and-drop
και φίλτρα
Η εφαρμογή θεωρείται αποδεκτή όταν:
1. Ο χρήστης μπορεί να μετακινεί εργαζόμενο σε ημέρα με drag-and-drop.
2. Μπορεί να προσθέτει πολλά παιδιά σε έναν φροντιστή.
3. Μπορεί να μετακινεί ολόκληρη ομάδα.
4. Μπορεί να αλλάζει τοποθεσία ομάδας με drag-and-drop.
5. Μπορεί να βλέπει όλη την εβδομάδα.
6. Μπορεί να βλέπει μόνο μία ημέρα.
7. Μπορεί να φιλτράρει ανά εργαζόμενο.
8. Μπορεί να φιλτράρει ανά παιδί.
9. Μπορεί να φιλτράρει ανά τοποθεσία.
10. Μπορεί να φιλτράρει ανά κατάσταση.
11. Οι drag-and-drop κινήσεις ελέγχονται αυτόματα για λογικά λάθη.
12. Υπάρχει undo/redo.

35. Έλεγχος λογικών σφαλμάτων και
διπλοπροσθηκών
35.1 Γενική αρχή
Η εφαρμογή πρέπει να διαθέτει κεντρικό validation engine που εκτελείται:
- κατά την εισαγωγή δεδομένων,
- κατά το drag-and-drop,
- πριν από την αποθήκευση,
- πριν από την οριστικοποίηση,
- πριν από την έγκριση,
- πριν από τη μαζική εισαγωγή,
- κατά τη συγχώνευση λιστών,
- κατά την παραλαβή αγορών.
Ο έλεγχος πρέπει να διακρίνει:
- hard errors,
- warnings,
- informational notices,
- duplicate suggestions,
- admin-overridable conflicts.

37. Γρήγορη και εύκολη διαχείριση αγορών
37.1 Quick Shopping Mode
Το tab “Ψώνια” πρέπει να είναι εξαιρετικά γρήγορο.
Κάθε item πρέπει να έχει μεγάλα κουμπιά:
- Αγοράστηκε
- Δεν υπήρχε
- Μερικώς
- Αντικαταστάθηκε
- Ακύρωση
Με ένα tap ο χρήστης αλλάζει status.
37.2 Swipe actions
Σε κινητό:
- swipe δεξιά = αγοράστηκε,
- swipe αριστερά = δεν υπήρχε,
- long press = μερικώς/αντικατάσταση/σημείωση.
37.3 Bulk completion

----- page 9 -----
Να μπορεί ο χρήστης:
- να επιλέξει πολλά items,
- να τα σημειώσει όλα “Αγοράστηκε”,
- να τα μεταφέρει όλα στο inventory,
- να τα αφαιρέσει από τη λίστα,
- να μεταφέρει τα μη διαθέσιμα στην επόμενη εβδομάδα.
37.4 Αφαίρεση από τη λίστα
Όταν ένα προϊόν ολοκληρωθεί:
- παραμένει στο ιστορικό,
- φεύγει από την ενεργή λίστα,
- μετακινείται στην ενότητα “Ολοκληρωμένα”,
- δεν διαγράφεται πραγματικά.
37.5 Λίστες βάσει προτύπων
Να υπάρχουν templates:
- εβδομαδιαία βασικά,
- καθαριστικά,
- πρωινό,
- φρούτα/λαχανικά,
- κρέατα,
- παιδικά είδη,
- προσωπική υγιεινή,
- Villa,
- Limenaria.
37.6 Δημιουργία από προηγούμενες λίστες
Να μπορεί να δημιουργηθεί νέα λίστα από:

----- page 10 -----
- προηγούμενη εβδομάδα,
- μέσο όρο τελευταίων 4 εβδομάδων,
- χαμηλά αποθέματα,
- συχνά αγοραζόμενα,
- items που δεν υπήρχαν,
- AI suggestion.
37.7 Αυτόματη αφαίρεση βάσει stock
Πριν προστεθεί item στη λίστα, το σύστημα πρέπει να ελέγχει:
- υπάρχει ήδη αρκετή ποσότητα;
- υπάρχει αναμενόμενη παραλαβή;
- υπάρχει duplicate στην ίδια λίστα;
- υπάρχει το ίδιο item σε άλλη λίστα;
- υπάρχει substitute διαθέσιμο;
Ο χρήστης πρέπει να μπορεί να κάνει override.

40. Νέα acceptance criteria
1. Δεν μπορεί να δημιουργηθεί ίδια ανάθεση δύο φορές χωρίς warning.
2. Δεν μπορεί να προστεθεί το ίδιο παιδί δύο φορές στην ίδια ομάδα.
3. Δεν μπορεί να δημιουργηθεί ίδιο inventory transaction από διπλό click.
4. Υπάρχει πλήρες Activity Tab.
5. Όλες οι αλλαγές δείχνουν before/after.
6. Οι αγορές ολοκληρώνονται με ένα tap.
7. Υπάρχει bulk completion.
8. Τα ολοκληρωμένα items δεν διαγράφονται αλλά αρχειοθετούνται.
9. Οι λίστες δημιουργούνται από templates και stock.
10. Τα conflicts μεταξύ δύο χρηστών εμφανίζονται καθαρά.
11. Το σύστημα διαχειρίζεται offline και retry χωρίς duplicates.
12. Όλα τα critical operations είναι idempotent.
13. Τα filters δεν αποκρύπτουν ενεργό error χωρίς ένδειξη.
14. Υπάρχει override μόνο με αιτιολογία.
15. Κάθε override εμφανίζεται στο Activity Tab.

42. AI Chatbot με μνήμη και πλήρη γνώση του
συστήματος
42.1 Σκοπός

- τις βάρδιες,
- τα παιδιά,

- τα events,

42.2 Παραδείγματα ερωτήσεων
- Ποιος είναι σήμερα στη Villa;
- Ποια παιδιά είναι στα Λιμενάρια;

42.3 Μνήμη AI
Το AI πρέπει να έχει δύο επίπεδα μνήμης:
Session memory
Θυμάται τη συζήτηση της τρέχουσας συνεδρίας.

49. Επιπλέον edge cases για AI, events,
φωτογραφίες και shared inventory
49.1 AI
- το AI δίνει απάντηση από παλιά δεδομένα,
- δεν έχει δικαίωμα πρόσβασης,
- δύο records έχουν ίδιο όνομα,
- η μνήμη περιέχει παλιά πληροφορία,
- το AI προτείνει λάθος αλλαγή,
- conflict μεταξύ AI πρότασης και πραγματικού schedule,
- request για ευαίσθητα δεδομένα από μη εξουσιοδοτημένο χρήστη.
49.2 Events
- event χωρίς διαθέσιμο προσωπικό,
- event με παιδί που είναι absent,
- event με overlapping schedule,
- event χωρίς approval,
- event αλλάζει μετά τη δημοσίευση,
- event ακυρώνεται,
- event μεταφέρεται σε άλλη ώρα,
- event δεν έχει υλικά,
- event απαιτεί αγορά που δεν έγινε,
- event έχει φωτογραφίες με περιορισμένη πρόσβαση.
49.3 Photos
- λάθος φωτογραφία,
- φωτογραφία ανηλίκου σε λάθος visibility,
- duplicate upload,

----- page 34 -----
- μεγάλη ανάλυση,
- unsupported file,
- φωτογραφία χωρίς linked record,
- ανάγκη διαγραφής για GDPR,
- deleted entity με retained audit evidence.
49.4 Shared inventory
- προϊόν ανήκει στο κοινό σπίτι αλλά μπήκε σε λάθος ψυγείο,
- μεταφορά μεταξύ Ψυγείου Κοριτσιών και Ψυγείου Φροντιστών,
- κοινή αγορά αλλά ξεχωριστή κατανάλωση,
- ίδιο προϊόν και στα δύο ψυγεία,
- συνολικό stock σωστό αλλά επιμέρους λάθος,
- κοινή αποθήκη με reserved ποσότητα,
- προϊόν αγοράστηκε για κορίτσια αλλά χρησιμοποιήθηκε από προσωπικό,
- προϊόν χωρίς σαφή ownership category,
- stock count σε ένα ψυγείο ενώ γίνεται μεταφορά από άλλο χρήστη.

55. Συνολικός μηχανισμός πρόληψης
σφαλμάτων, bugs και ασυνεπειών
55.1 Κεντρική αρχή αξιοπιστίας
Το σύστημα πρέπει να θεωρεί ότι ο χρήστης μπορεί να πατήσει δύο φορές το ίδιο
κουμπί, δύο χρήστες μπορεί να αλλάξουν τα ίδια δεδομένα ταυτόχρονα, η σύνδεση
μπορεί να κοπεί οποιαδήποτε στιγμή, ένα AI αποτέλεσμα μπορεί να είναι λάθος, μία
λίστα μπορεί να διαβαστεί λανθασμένα και ένα record μπορεί να είναι τεχνικά έγκυρο
αλλά επιχειρησιακά παράλογο.
Απαιτούνται ταυτόχρονα:
- client-side και server-side validation,
- database constraints,
- idempotency keys,
- audit trail,
- duplicate prevention,
- confirmation για κρίσιμες αλλαγές,
- undo όπου είναι ασφαλές,

----- page 45 -----
- reconciliation jobs,
- admin review queues.
55.2 Κατηγορίες σφαλμάτων
Hard error
Η αποθήκευση απαγορεύεται, π.χ. λήξη βάρδιας πριν από την έναρξη, ίδιο παιδί δύο
φορές στην ίδια ομάδα, αρνητικό stock χωρίς correction, μη εξουσιοδοτημένη
πρόσβαση ή inventory transaction χωρίς προϊόν.
Warning
Η ενέργεια επιτρέπεται μόνο μετά από επιβεβαίωση, π.χ. πολύ μεγάλη ομάδα για έναν
φροντιστή, αλλαγή τελευταίας στιγμής, προϊόν που υπάρχει ήδη σε επαρκές stock ή
event χωρίς υλικά.
Informational notice
Η ενέργεια επιτρέπεται, αλλά εμφανίζεται χρήσιμη πληροφορία, π.χ. το ίδιο προϊόν
αγοράστηκε την προηγούμενη εβδομάδα ή υπάρχει event που πιθανόν το χρειάζεται.

57. Επιπλέον edge cases ψυγείων, αποθήκης και
προμηθειών
57.1 Canonical προϊόντα και aliases
Το ίδιο προϊόν μπορεί να εμφανίζεται ως «Γάλα», «Γάλα light», «Milch light», «Light
milk» ή «γάλα 1,5%».
Κάθε προϊόν πρέπει να έχει:
- canonical product,
- aliases,
- normalized name,
- category,
- brand,
- package size,
- unit,
- barcode όπου υπάρχει.
Δεν επιτρέπεται αυτόματη συγχώνευση όταν δεν υπάρχει αρκετή βεβαιότητα.
57.2 Μονάδες μέτρησης
Υποστηρίζονται τεμάχια, πακέτα, κιλά, γραμμάρια, λίτρα, ml, κουτιά, μπουκάλια,
σακούλες και ρολά.
Edge cases:
- 2 πακέτα x 6 τεμάχια,

----- page 48 -----
- 1,5 kg,
- 500 g και 0,5 kg,
- ανοιγμένο ή μισό πακέτο,
- διαφορετικά μεγέθη συσκευασίας,
- μη ασφαλής μετατροπή χωρίς package metadata.
57.3 Ακεραιότητα stock
Πρέπει να αποτρέπονται:
- αρνητικό stock,
- διπλή παραλαβή ή αφαίρεση,
- transfer χωρίς αντίστοιχη αφαίρεση από source,
- item σε λάθος storage zone,
- expired προϊόν ως διαθέσιμο,
- προϊόν που χρησιμοποιήθηκε ενώ ήταν reserved,
- αλλαγή ποσότητας χωρίς transaction.
Οι μεταφορές γίνονται ως μία atomic database transaction.
57.4 Shared house inventory
Για το Ψυγείο Κοριτσιών, το Ψυγείο Φροντιστών και την Κοινή Αποθήκη απαιτούνται:
- κοινή συνολική εικόνα,
- ξεχωριστή φυσική θέση,
- ξεχωριστό ιστορικό κατανάλωσης,
- εσωτερικές μεταφορές,
- αποφυγή διπλού υπολογισμού,
- διάκριση ownership/use category από physical location.
57.5 Φωτογραφίες inventory
Η φωτογραφία αποτελεί τεκμηρίωση, όχι μοναδική πηγή αλήθειας. Πρέπει να
χειρίζεται φωτογραφία λάθος ψυγείου, παλιού stock, duplicate upload, αποτυχημένο
upload, media server offline και φωτογραφία χωρίς σύνδεση με απογραφή.

58. AI για ανάγνωση λιστών αγορών
58.1 Υποστηριζόμενες πηγές
Το AI πρέπει να διαβάζει:
- απλό κείμενο,
- επικολλημένο μήνυμα,
- φωτογραφία χειρόγραφης ή τυπωμένης λίστας,
- PDF,
- screenshot,
- TXT,
- CSV,
- Excel,
- email content,
- προηγούμενη λίστα της εφαρμογής.
58.2 AI extraction pipeline
1. Upload ή επικόλληση.
2. Ανίχνευση τύπου αρχείου.
3. Εξαγωγή κειμένου.
4. Ανίχνευση γλώσσας.
5. Διάσπαση σε προϊόντα.
6. Αναγνώριση ποσότητας και μονάδας.
7. Αναγνώριση brand και package size.
8. Κατηγοριοποίηση.
9. Αντιστοίχιση με canonical product.
10. Έλεγχος duplicates.
11. Έλεγχος υπάρχοντος και αναμενόμενου stock.
12. Προβολή draft.
13. Ανθρώπινη επιβεβαίωση.
14. Αποθήκευση στην ενεργή λίστα.
15. Αρχειοθέτηση του αρχικού αρχείου και του extracted text.

----- page 50 -----
58.3 Confidence score
Κάθε extracted item έχει:
- υψηλή,
- μέτρια,
- χαμηλή βεβαιότητα.
Σε χαμηλή βεβαιότητα ζητείται επιβεβαίωση. Παράδειγμα: «Νερά μεγάλα 4» σημαίνει
4 μπουκάλια ή 4 εξάδες;
58.4 Duplicate detection από AI
Το AI πρέπει να αναγνωρίζει ότι:
- Nutella x2,
- 2 Nutella,
- Nutella δύο φορές
πιθανόν είναι μία εγγραφή ποσότητας 2.
Δεν συγχωνεύει αυτόματα προϊόντα διαφορετικού brand, μεγέθους ή τύπου.
58.5 Έλεγχος stock πριν από την αγορά
Για κάθε πρόταση εμφανίζονται:
- τρέχον stock,
- αναμενόμενο stock,
- μέση εβδομαδιαία κατανάλωση,
- εκτιμώμενες ημέρες επάρκειας,
- προτεινόμενη ποσότητα αγοράς.
Το AI δεν αφαιρεί αυτόματα προϊόν από τη λίστα μόνο επειδή υπάρχει stock.
58.6 Αρχειοθέτηση και versioning

----- page 51 -----
Για κάθε εισαγόμενη λίστα αποθηκεύονται:
- αρχικό αρχείο,
- uploader,
- ημερομηνία/ώρα,
- extracted text,
- AI αποτέλεσμα,
- confidence ανά item,
- διορθώσεις χρήστη,
- τελική approved list,
- version history.
58.7 AI learning από διορθώσεις
Το AI μπορεί να μαθαίνει οργανωτικά:
- aliases,
- συνηθισμένες μονάδες,
- brands,
- ποσότητες,
- συχνά OCR λάθη.
Δεν αλλάζει ιστορικά records και δεν εκτελεί αλλαγές χωρίς επιβεβαίωση.

62. Νέα acceptance criteria αξιοπιστίας

----- page 55 -----
1. Το ίδιο API request δεν δημιουργεί δεύτερη εγγραφή.
2. Δύο ταυτόχρονες αλλαγές παράγουν conflict dialog.
3. Η μεταφορά stock είναι atomic.
4. Το AI δεν αποθηκεύει λίστα χωρίς ανθρώπινη επιβεβαίωση.
5. Κάθε AI item έχει confidence score.
6. Η αρχική λίστα και οι διορθώσεις αρχειοθετούνται.
7. Υποστηρίζονται aliases προϊόντων.
8. Υποστηρίζονται ελληνικά και γερμανικά στην ίδια λίστα.

11. Κάθε κρίσιμη ενέργεια έχει idempotency key.
12. Υπάρχει καθημερινό και εβδομαδιαίο reconciliation.
13. Low-confidence AI εγγραφές δεν περνούν αυτόματα.
14. Failed uploads δεν αφήνουν ψεύτικα ολοκληρωμένα records.
15. Το Activity Tab καταγράφει AI extraction, ανθρώπινη διόρθωση και τελική έγκριση.
